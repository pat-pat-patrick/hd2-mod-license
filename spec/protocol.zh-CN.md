# HD2 Mod License 协议（草案 1，2026-11-02）

MOD 作者用它把 MOD 限定给自己的会员使用。会员在管理器中登录作者的发证服务器，取得签名的授权文件；MOD 在游戏加载时用作者的公钥离线核对。游戏运行时不联网。

## 角色

| 角色 | 做什么 | 实现 |
|---|---|---|
| 发证方 | 判断会员身份，签发、续期授权 | 签发服务，使用该创作者自己的密钥；不在本仓库中 |
| 管理器 | 读取 MOD 的声明，登录、取回、续期、写入授权 | HD2 Mod Quick Deploy 的授权插件 |
| MOD | 加载时核对授权 | `lua/license_check.lua` |

每个发证方以自己的主机名区分，例如 `license.example.com`，下文称为「发证方名称」。

## 1. MOD 的声明

需要授权的 MOD 在包的根目录放 `hd2_license.json`：

```json
{
  "protocol": 1,
  "issuer": "license.example.com",
  "name": "作者或频道名称",
  "key": "<RSA-2048 公钥模数 n，十六进制>"
}
```

- `issuer`：发证方名称，只含小写字母、数字、`.` 和 `-`。管理器访问 `https://<issuer>/`。
- `name`：管理器显示给玩家的名称。
- `key`：与 MOD 内嵌的公钥相同，必须是 RSA-2048（去掉前导 0 后正好 512 位十六进制，最高位为 1）。其他长度的公钥，管理器和 MOD 的检查都不接受。签发方提供这个文件，`tools/build_check.py` 读取它，为 MOD 构建内嵌公钥的检查。

## 2. 游戏账号标识

授权绑定的是游戏账号，不是电脑。

- **游戏内：** `Network.peer_id()`，16 位十六进制（不足 16 位时在左侧补 0）。
- **管理器：** `%APPDATA%\Arrowhead\Helldivers2\saves\` 中 `<标识>_user_settings.config` 的文件名前缀。一台电脑上可能有多个。

两者是同一个值（已证实：同一账号自 2026-09-23 起，跨越 10-20 的游戏补丁，值始终不变）。

有效位不足 8 位的标识（前 8 位都是 0，例如游戏尚未给出账号时的 `0`）不算账号：管理器不把它发给发证方，MOD 的检查把它当作 `no_account`。发证方也应拒绝绑定这样的标识。

## 3. 发证方接口

登录采用原生应用的 OAuth 做法（RFC 8252：本机回调加 PKCE）：浏览器登录完成后回到发起登录的那台电脑，授权只交给持有 verifier 的管理器。

所有响应为 JSON，`/login` 与 `/callback` 除外。

| 请求 | 用途 | 成功 | 失败 |
|---|---|---|---|
| `GET /login?c=<challenge>&s=<state>&port=<端口>&acct=<标识>[,<标识>]` | 管理器在浏览器中打开；跳转到会员平台登录 | 302 | 400 页面 |
| `GET /callback` | 会员平台登录后回到发证方；发证方再让浏览器跳转到 `http://127.0.0.1:<端口>/done?s=<state>&code=<code>`，失败时为 `&error=<值>`（`account_limit` 时附 `wait_days`） | 302 | 400 页面（登录已过期） |
| `POST /claim {"code", "verifier"}` | 管理器用回调带来的 code 领取授权，只能领一次 | `{"license", "renew"}` | 403 `{"error"}`（`account_limit` 时可附 `wait_days`） |
| `POST /renew {"renew": "<续期凭据>"}` | 到期前续期 | `{"license"}` | 403 `{"error"}` |

- **登录流程：**
  1. 管理器在 `127.0.0.1` 上监听一个由系统分配的端口 `port`；生成 `verifier`（32 个随机字节，64 位十六进制，只留在本机）、`c`（`verifier` 的 SHA-256，64 位十六进制）和 `s`（32 位十六进制随机数）。
  2. 浏览器打开 `/login`，再到会员平台登录。登录后，发证方核对会员资格，并检查这些账号能否绑定，但**此时不改变绑定**。然后发出一次性的 `code`（32 位十六进制，10 分钟内有效），让浏览器跳回 `127.0.0.1:<port>/done`。
  3. 管理器只接受 `s` 与自己一致的 `/done` 请求，其他请求一律回 404。随后用 `{code, verifier}` 调用 `/claim`。发证方核对 `SHA-256(verifier) == c` 之后，才绑定账号、签发授权。无论核对是否通过，`code` 都只能用一次。最后管理器在浏览器里显示登录结果页。
- **为什么这样做：** 如果有人自己生成登录链接，诱骗会员打开并登录，浏览器会跳回会员**自己电脑**上的端口，而那里没有程序在监听。做链接的人拿不到 `code`，什么也领不到，会员的绑定也不会改变。
- **旧流程已停用：** 协议第 1 版的登录方式（`/login?n=`，`/claim {"n"}`）任何做链接的人都能领取，已经停用。发证方对旧流程的登录页面提示更新插件，对 `/claim {"n"}` 回答 `update_plugin`。续期接口 `/renew` 没有变化。
- `renew`：64 位十六进制，管理器按会员（授权的 `holder`）分别保存在自己的数据中，不放进游戏目录。同一会员重新登录后，其旧凭据失效。
- `error` 的取值：

| 值 | 含义 | 管理器的处理 |
|---|---|---|
| `not_member` | 不是有效会员，或档位不够 | 提示玩家，停止续期 |
| `account_limit` | 已绑定的游戏账号达到上限，且还不能更换（可附 `wait_days`：还需等待的天数） | 提示等待后再换，或联系作者 |
| `denied` | 玩家在会员平台拒绝了授权 | 提示可重新登录 |
| `sign_in_again` | 续期凭据仍有效，但需要重新登录 | 提示重新登录 |
| `unknown` | 续期凭据无效；或 `/claim` 的 code 无效、已用过，或与 verifier 不符 | 提示重新登录 |
| `update_plugin` | 管理器的插件仍在使用已停用的旧登录流程 | 提示更新插件 |

## 4. 授权文件

管理器写入 `%APPDATA%\Arrowhead\Helldivers2\licenses\<issuer>.txt`。每份授权原样保存发证方返回的文本，格式如下：

```
HD2 MOD LICENSE 1
issuer=<发证方名称>
accounts=<标识>[,<标识>]
issued=<unix 时间>
expires=<unix 时间>
holder=<发证方自定的持有人标识>
sig=<签名，十六进制>
```

- **签名：** RSASSA-PKCS1-v1_5，SHA-256，RSA-2048，覆盖 `sig=` 行之前的全部字节。
- **换行：** 签名时为 LF。检查时去掉 CR，所以被编辑器改成 CRLF 不影响。
- **`issued`：** 必须有。玩家电脑的时间比 `issued` 早超过一天时，检查返回 `clock`（允许一天的误差，是为了避免时钟稍有偏差的电脑用不了刚签发的授权）。
- **未知字段：** 检查方忽略，但它们在签名范围内。
- **多位会员：** 一个文件可以依次存放多份授权，每位在这台电脑上登录过的会员一份（例如两名玩家共用一台电脑）。每份以位于行首的 `HD2 MOD LICENSE 1` 开始。只要其中一份通过检查，MOD 就可以使用。

## 5. 管理器的行为

1. 添加或更新 MOD 时读取 `hd2_license.json`，在 MOD 列表中标出需要授权、已授权或已过期。
2. 第一次向某个发证方登录前，告诉玩家发证方名称，以及游戏账号标识会发送给它。
3. 登录时按第 3 节的流程，在 `127.0.0.1` 上监听浏览器的回调。玩家取消、超时或浏览器无法打开时，停止监听。
4. 记住每个发证方第一次见到的公钥。之后若有 MOD 对同一发证方声明了不同的公钥，提醒玩家，不自动采用。
5. 会员登录或续期后，用新授权替换该会员（相同 `holder`）的旧授权；其他会员仍然有效的授权保留，已过期的删除。
6. 每份授权剩余有效期不足一半时，用该会员的续期凭据在后台续期。某位会员续期失败，不影响其他会员。
7. 先写入临时文件再改名，避免游戏读到写了一半的文件。

## 6. MOD 的行为

1. 嵌入用 `tools/build_check.py` 为本 MOD 构建的检查。构建时把发证方名称和公钥写进源码，再做混淆；每次构建的布局都不同。MOD 的 Lua 里不再单独存放公钥，各个 MOD 带的检查文件也互不相同。
2. 加载这个文件后，立即把 `check` 存为自己的局部变量，再调用一次 `check()`，不在每帧调用。一次约 9 ms（PUC Lua 5.1，游戏内实测，2026-11-02）。文件里有多份授权时，只有写着当前账号且未过期的那份才验签，所以耗时不随会员数增加。
3. 返回 `no_account` 时，游戏还没有给出账号标识，稍后再试。
4. 检查只信任游戏和 Lua 自身提供的 C 函数。检查在加载时就取好要用的库函数；运行时要求 `peer_id`、`os.time`、`os.getenv`、`io.open` 和它自己用的工具都是 C 函数，并且不是包着脚本值的 C 函数（例如 `coroutine.wrap`、`string.gmatch`、`io.lines`、`io.read`），否则返回 `tampered`。这样，只替换一个函数来伪造账号标识或时间的脚本，就不能让复制来的授权通过检查（更完整的伪造见“限制”）。这需要 `debug.getinfo`。游戏的 Lua 没有它时，检查返回 `no_debug`；这种情况下改用 `--no-debug` 构建，检查就只能区分 Lua 函数和 C 函数。新构建要先在未改动的游戏里试一次。
5. 其他失败：原因见下表。怎么处理由作者决定，建议写入日志并不启动功能。

| 原因 | 含义 |
|---|---|
| `missing` | 没有授权文件 |
| `malformed` | 文件格式不对 |
| `issuer` | 授权来自另一个发证方 |
| `signature` | 签名不对：被改过，或不是这个公钥签的 |
| `expired` | 已过期 |
| `clock` | 电脑时间比授权签发时间早超过一天 |
| `account` | 没有一份授权写着当前游戏账号 |
| `key` | 内嵌的公钥不是 RSA-2048 |
| `tampered` | 检查读取游戏信息所用的函数被脚本替换了 |
| `no_debug` | 游戏的 Lua 没有 `debug.getinfo`：改用 `--no-debug` 构建 |

## 限制

- 签名保证授权无法伪造。但 MOD 的 Lua 可以被修改，修改者可以删除检查。本协议阻止的是把文件直接复制给他人。
- 检查用的是玩家电脑的时间。把系统时间调回到授权有效期内，仍可延长使用；但不能调到签发之前超过一天。授权有效期越短，这种做法的收益越小。
- `tampered` 只能挡住只替换一个函数的脚本。一段约十行的脚本，只要比 MOD 先加载，先把 `debug.getinfo` 换成对伪造函数和对它自己都回答“C 函数”的假函数，再伪造 `peer_id`，就能让复制来的授权通过检查（2026-11-05 在 PUC 5.1 上复现）。这段脚本不针对哪个 MOD，对每个 MOD 的构建都同样有效；能控制 MOD 代码块加载方式（它的环境、`loadstring`）的脚本也一样。检查在 MOD 自己的 Lua 里运行，而在它之前加载的脚本可以改动它能看到的一切，所以这一点无法从检查内部补上。真正的防护靠混淆，以及每个 MOD 各用一个构建：删掉或改动检查需要逐个 MOD 去做。
- 发证方能看到玩家的游戏账号标识，以及玩家在会员平台的身份。

## 版本

协议版本号写在授权文件首行（`HD2 MOD LICENSE 1`）和 `hd2_license.json` 的 `protocol` 中。不兼容的修改会使用新的版本号。

静态资源 MOD（无 Lua 代码，套不上第 6 节的游戏内核对）的保护与追溯，见扩展 [static-resources.zh-CN.md](static-resources.zh-CN.md)。
