# HD2 Mod License 协议扩展：静态资源 MOD（草案 1，2026-11-03）

本扩展建立在[协议第 1 版](protocol.zh-CN.md)之上，解决**静态资源 MOD**（贴图、模型、音频等纯数据，没有 Lua 代码）的保护与追溯。它不改动第 1 版的任何部分；一个 MOD 可以同时是 Lua MOD（用 `license_check.lua` 在加载时核对）和静态资源 MOD（用本扩展）。

## 0. 为什么需要扩展

第 1 版的全部保护挂在一个代码执行点上：MOD 的 Lua 在加载时跑一次 `check()`。静态资源 MOD 没有代码执行点，套不上。而且游戏要渲染资源，就必须读到明文字节——明文一旦落到游戏目录或内存，取得授权的人就能导出它。

所以本扩展不追求「取得授权者也无法导出明文」（做不到），而是把目标定在两件可做到的事上：

1. **门控下发：** 可部署的内容只能经授权通道取得。非会员即使拿到分发包，也得不到解开它的密钥。
2. **明文追溯：** 每一位会员取得的内容都带着**按账号分配的不可见指纹**（数字水印）。明文泄露后，可以从内容本身验出它当初发给了哪个账号。

威胁模型与第 1 版一致：阻止把分发包直接复制给他人；不阻止取得授权者从自己的游戏目录导出明文，但要让每一份导出都带着可追溯到来源账号的指纹。

**关键区分：加密保护的是密文容器，追溯靠的是内容里的水印。** 任何写在文件头、元数据或签名收据里的「是谁」，都会在导出明文时一并丢失；明文泄露后仍然活着的只有嵌进内容本身（像素／顶点／波形）的水印。

## 1. 名词

| 名词 | 含义 |
|---|---|
| 封装（seal） | 用内容密钥对称加密后的包 |
| 内容密钥 `K_c` | 每份封装包一个，32 字节随机 |
| 指纹码字（codeword） | 发证方按 (账号, 内容) 分配的秘密比特串，取自抗合谋指纹码 |
| 水印（watermark） | 把码字鲁棒地嵌入内容明文 |
| 收据（receipt） | 发证方对一次下发的签名声明 |
| 基包（base） | 所有账号相同、仍需封装的公共部分（可选，见 6.3） |

## 2. MOD 的声明扩展

静态资源 MOD 在 `hd2_license.json` 里增加一个 `payload` 块：

```json
{
  "protocol": 1,
  "issuer": "license.example.com",
  "name": "作者或频道名称",
  "key": "<RSA-2048 公钥模数 n，十六进制>",
  "payload": {
    "kind": "static",
    "id": "<内容标识>",
    "deploy": "<部署清单名或相对路径>"
  }
}
```

- 有 `payload` 块，表示这是（或同时也是）静态资源 MOD。管理器据此知道要向发证方**取回封装包**，而不是（或不只是）核对 Lua 授权。
- `issuer`、`name`、`key` 与第 1 版同义，`key` 既用于验证授权（如果同时是 Lua MOD），也用于验证本扩展的收据签名。
- `id`：该发证方命名空间内的内容标识，区分同一发证方的多个静态 MOD 或版本。
- `deploy`：管理器把解开的内容放到游戏哪里的约定（清单名或相对 MOD 目录的路径）。
- **分发包里不含可部署的明文。** 公开分发的 MOD 包只含 `hd2_license.json`，外加可选的公共基包（已封装，见 6.3）。真正可部署的内容来自发证方。
- **旧管理器**（不认识 `payload`）必须把该 MOD 标为「需要更新管理器」，**不得**当作无授权直接部署——因为包里根本没有明文可部署。

## 3. 发证方接口扩展

在第 1 版三个接口之外，新增一个取回封装包的接口。鉴权复用会员的续期凭据（`renew`，见第 1 版第 3 节）：会员已经登录过，取回封装包由同一份凭据授权，账号绑定也由它证明。

| 请求 | 用途 | 成功 | 失败 |
|---|---|---|---|
| `POST /payload {"id", "account", "renew"}` | 取回某账号的指纹封装包 | `{"url", "key", "hash", "receipt"}` | 403 `{"error"}` |

- 请求：`id` 为声明里的内容标识；`account` 为要部署的游戏账号标识（16 位十六进制，必须在该 `renew` 持有人的有效授权账号内）；`renew` 为续期凭据。
- 成功响应：
  - `url`：下载封装字节的地址（二进制走普通 HTTP GET，不塞进 JSON）。可为一次性或限时链接。
  - `key`：`K_c`，十六进制，仅在 TLS 加 `renew` 鉴权之后下发。
  - `hash`：封装字节的 SHA-256，供管理器核对下载是否完整。等于收据里的 `sealed_hash`。
  - `receipt`：签名收据，格式见第 5 节。
- 发证方收到请求后：核对会员仍然有效、`account` 在其授权内；为 `(account, id)` 取得（或现做）指纹封装包；返回上述字段。
- `/payload` 只读，不消耗也不轮换 `renew`（`renew` 只在重新登录时轮换）。但发证方应限制同一会员为过多不同账号取指纹包（反刷，见第 8 节 `payload_limit`）。

## 4. 封装

- 对称加密：AES-256-GCM 或 XChaCha20-Poly1305。`K_c` 每份独立随机，随封装提供 nonce；用 AEAD 的认证标签保证完整性。
- `K_c` 只经 `/payload` 响应下发，在 TLS 加 `renew` 鉴权之后。**得不到 `K_c` 就解不开**——这就是「必须经授权通道」的实现：非会员即使拿到 `url` 指向的密文，也没有 `K_c`。
- **上限：** `K_c` 一旦到达管理器，就在用户机器上。加密只挡「拿到密文但没经过鉴权的人」，不挡已经鉴权的用户。已授权用户导出明文属于范围之外，靠第 6 节的水印追溯，不靠加密阻止。

## 5. 收据

发证方对一次下发的签名声明，格式与授权文件同类：

```
HD2 PAYLOAD RECEIPT 1
issuer=<发证方名称>
account=<16 hex>
id=<内容标识>
mark=<指纹句柄，十六进制>
sealed_hash=<封装字节的 SHA-256>
issued=<unix 时间>
sig=<RSASSA-PKCS1-v1_5，SHA-256，覆盖 sig= 行之前全部字节>
```

- **签名：** 与授权文件相同的算法和公钥（声明里的 `key`）。管理器用它验签，并确认 `account`、`id`、`sealed_hash` 与本次请求和下载相符。
- `mark`：指向发证方记录中码字的**不透明句柄**，便于事后由句柄查码字、查账号。它**不是码字明文**——放进收据只为审计关联，不泄露水印内容。
- **收据只溯源封装包，不溯源明文。** 它证明「这份封装包由该发证方为该账号下发」（provenance）。内容一旦部署成游戏明文，收据不在其中，所以明文泄露后的追溯**只能**靠第 6 节的水印。

## 6. 指纹与水印（追溯的核心）

### 6.1 码字：抗合谋指纹码

- 发证方为每个 `(账号, id)` 分配一个秘密码字，取自**抗合谋指纹码**（推荐 Tardos 码）。
- 抗合谋人数 `c`（要抵抗的合谋规模）与误指控概率 `ε` 决定码长 `m`。Tardos 码的数量级为 `m ≈ 100 · c² · ⌈ln(1/ε)⌉` 比特（具体常数见实现）。
- 发证方离线保存 `{句柄 → 码字 → 账号}` 的映射，不下发。

### 6.2 嵌入：必须在服务端

- 水印**必须由发证方在封装之前嵌入明文**。
- 管理器在任何时候都**不得持有未加水印的明文，也不得在本地嵌入水印**。管理器跑在要追踪的人自己的机器上；让它参与水印，等于把去水印的能力交给对方。
- 嵌入要求：对游戏资源管线（DDS／BC 贴图压缩、网格重导出、音频重采样）鲁棒；对正常游戏使用不可感知；检测可用盲检测，或由发证方自留无水印原件做非盲检测（更鲁棒，推荐）。
- 容量：被嵌内容要能装下 `≥ m` 比特，且经上述管线后仍可恢复。

### 6.3 哪些资源打指纹

- 不必给每个资源都打。可只给少数鲁棒、容量足够的资源（大贴图、主模型、长音频）打满 `m` 比特，其余作为**公共基包**对所有账号相同。
- 这样每账号唯一的字节只有被打指纹的那部分；基包虽仍封装、仍需 `K_c`，但对所有账号相同，可公开缓存／CDN，降低发证方按账号生成和分发的成本。
- **代价省不掉的部分：** 打指纹的那些资源必须按账号现做，这是服务端成本的下限。

### 6.4 追溯

- 发现疑似泄露的明文 → 从内容恢复出码字比特（可能残缺，或被合谋加了噪声）→ 用指纹码的追踪算法输出被指控账号。
- Tardos 码在合谋人数 `≤ c` 时，以 `≥ 1-ε` 的概率不冤枉无辜，并至少指出一名合谋者。**超过 `c`，保证失效**：可能查不出，也可能误指控。所以 `c` 要按真实风险定得偏高，代价是码长、容量需求和生成成本都随之上升。

## 7. 管理器的行为（扩展）

1. 读到带 `payload` 的声明，该 MOD 走静态资源流程。
2. 会员登录后（复用第 1 版的登录／续期），对每个要部署的账号调用 `/payload`。
3. 校验收据签名（用声明里的 `key`）、`account`、`id`、`sealed_hash`；下载 `url` 的封装字节，核对 `hash`；用 `key` 解封装。
4. 按 `deploy` 把内容部署到游戏的 patch 路径。
5. **缓存：** 管理器可缓存封装包与 `K_c` 以便离线重部署。这意味着明文可从游戏目录或缓存导出——在范围之内（同第 1 版「不阻止导出，只追溯」）。
6. **多账号同机：** 每个已登录账号各取各自的指纹包。实际部署进游戏的是其中一份，带的是**取得它的那个账号**的指纹；同机换账号游玩不改变追溯目标的定义（追的是「谁把这份拿出去的」）。

## 8. 错误值扩展

在第 1 版 `error` 取值之外，`/payload` 可返回：

| 值 | 含义 | 管理器的处理 |
|---|---|---|
| `payload_unknown` | 没有这个 `id` | 提示检查 MOD 版本或更新 |
| `payload_account` | 该账号不在有效授权内 | 提示先登录或续期该账号 |
| `payload_pending` | 该账号的指纹包尚未生成 | 稍后再试；持续不好转则联系作者 |
| `payload_limit` | 该会员已为过多不同账号取过指纹包 | 提示联系作者 |
| `banned` | 该会员或账号已被封禁（见第 9 节） | 提示联系作者；停止续期与取包 |

`not_member`、`sign_in_again`、`unknown`、`update_plugin` 沿用第 1 版第 3 节的含义与处理。`banned` 也可由第 1 版的 `/claim`、`/renew` 返回。

## 9. 封禁：追溯之后的惩罚

追溯（§6.4）查出泄露来源后，发证方可以封禁，让这个人失去服务：被封禁的会员或游戏账号，`/claim`、`/renew`、`/payload` 一律拒绝（返回 `banned`）。拿不到授权和封装包，加入的所有创作者的 MOD 都装不了、用不了。

**封禁只发生在发证方（服务端），键在账号层，不在硬件。** 这是经过权衡后的选择：

- **可执行：** 发证方不在用户机器上，是唯一拔不掉的执行点。
- **代价真实：** 账号层封禁让泄露者直接失去付费会员资格——这本身就是最实际的惩罚。
- **主键：** 会员（`holder`，如 `p:<Patreon 用户编号>`）与涉及的游戏账号。两者任一命中即拒。

### 9.1 封禁记录

发证方按 `holder` 和游戏账号各存一条记录，内含封禁原因、作为证据的指纹句柄 `mark`、时间，以及（可选）管理器上报的 `hwid`。加入的创作者之间**共享**这份名单：把记录复制到各自的发证方即可，被封者在任何一家都被拒。

### 9.2 必须带的约束

- **人工复核、可申诉、可撤销。** 追溯是概率性的（§6.4：Tardos 只把误指控概率压低，不归零；合谋还会加噪）。所以封禁由人确认后才下，并随时可解除；**不得**把不可逆的全网封禁自动挂在一次概率性指控上。
- **`hwid` 只是调查线索，不是封禁键。** 硬件标识可伪造（被封者改个指纹即“解封”），又会误伤重装、换硬件或二手转卖的无辜机器。所以记录里可以留 `hwid` 备查，但不据它拒绝。

### 9.3 明确的非目标

以下两项**本扩展不做**，因为在 HD2 上基本无法成立，且会误伤正常玩家：

- **不在客户端“封锁/破坏硬件”。** 游戏内的 Lua 沙箱读不到硬件标识；唯一能读的管理器运行在被封者自己的机器上，改掉它是最轻的绕过。
- **不强制“禁止虚拟机运行”。** Windows 11 的 VBS/HVCI 会让普通物理机也报告 hypervisor-present，云游戏、GPU 直通、Linux Proton 同样“像 VM”：强行拦截会挡掉一批真实付费玩家，而真要藏 VM 的人藏得掉。

威慑力来自“失去服务 + 可追溯”，不来自在敌对硬件上打一场赢不了的仗。

### 9.4 发证方接口（管理，需鉴权）

| 请求 | 用途 |
|---|---|
| `POST /admin/ban {holder?, accounts?, mark?, hwid?, reason}` | 封禁一个会员和／或一组游戏账号 |
| `POST /admin/unban {holder?, accounts?}` | 解除封禁 |

至少要给出 `holder` 或一个账号。鉴权与第 1 版的 `/admin/*` 相同。

## 10. 安全性质与限制

- **门控下发**是「必须经授权通道」的实现：非会员拿到密文没有 `K_c`。它**不是**「已授权用户也解不开」。
- **水印**是明文泄露后唯一的追溯手段；服务端嵌入是它成立的前提。
- **抗合谋到 `c`**；超过 `c` 保证失效。
- **水印鲁棒性尽力而为：** 重度重编码或重建资源可以抹掉水印，代价是可见的质量损失——与第 1 版「工作量相当于重做 MOD」同理。
- **收据只溯源封装包，不溯源明文。**
- **隐私成本上升：** 发证方从「签几行字」变为「按账号生成并分发二进制，并保存指纹映射和封禁名单」。它知道得更多、存得更多；跨创作者共享封禁名单还涉隐私与名誉风险（GDPR／PIPL），所以 §9.2 要求人工复核与可撤销。这是本扩展最大的一笔代价，作者要认。

## 附录（非规范）：各媒体的水印选型

本扩展只规定「服务端嵌入、鲁棒、盲或非盲、容量 `≥ m`」，不绑定具体算法。以下为选型参考，鲁棒性须按 HD2 实际资源管线实测：

- **贴图：** 变换域的扩频（spread-spectrum）嵌入，先嵌水印再做 BC 压缩；检测时对比发证方自留原件（非盲）。要扛住 BC1／BC7 的量化。
- **模型：** 顶点坐标、法线的受控微扰，或 UV 的小位移；要扛住重导出与网格精简，需保守的冗余。
- **音频：** 扩频或回声隐藏；要扛住重采样与有损压缩。

这些都是研究级工程，不是一蹴而就。

## 附录（非规范）：发证方的落地形态

参考实现把发证方做成 Cloudflare Worker（见私有 issuer 仓库）。它受两条现实约束，任何同类的无服务器/轻量发证方都会遇到：

- **计算：** Worker 跑不动对多 MB 资源的加密，尤其是格式相关的水印嵌入（重活、耗 CPU）。
- **存储：** KV 单值上限 25 MiB，且不适合放大二进制。

所以**封装和水印必须离线完成**（§4、§6.2 已要求水印在服务端嵌入；这里进一步说明"服务端"不等于"在 Worker 的请求里"）。落地时拆成两段：

1. **离线工具**（跑在发证方的机器上，不是 Worker）：为每个账号分配码字、嵌水印、封装、把封装字节上传到对象存储（如 R2）的 `payload/<id>/<mark>.seal`，并把元数据写入 KV：

   ```
   payload:<id>:<mark>  {hash, key}   封装字节的 SHA-256 和内容密钥 K_c
   mark:<id>:<account>  <mark>        某账号拿到的是哪个变体
   ```

   `{mark → 码字 → 账号}` 的追溯映射只留在这个离线工具里，不进 Worker、不进 KV。

2. **Worker 只做轻活：** `/payload` 复用 `renew` 鉴权（像 `/renew` 一样重新核对会员），核对账号已绑定，签一张收据，返回一个限时链接 + `K_c`；`/payload/blob` 凭短时令牌从对象存储把封装字节流式返回。某账号的变体尚未写入时，`/payload` 回 `payload_pending`。

这只是参考落地，不是协议要求。任何能以相同方式回答 `/payload` 的发证方都可以。

## 11. 版本

- 本扩展标记：**static-resources 草案 1**。
- 在声明中以 `payload` 块的存在开启；收据首行 `HD2 PAYLOAD RECEIPT 1` 带版本号。不兼容的修改使用新的版本号。
- 基础协议仍为 `protocol: 1`；本扩展不改动它。
